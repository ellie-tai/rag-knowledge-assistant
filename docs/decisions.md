## 已決定

### D1. 專案範圍
- **決定**：RAG 文件問答，完整版但分階段，每階段都能跑。
- **理由**：一次做完太難理解；分階段才能確保每一步都懂。

### D2. 參與方式
- **決定**：作者主導需求、架構與決策；AI（Claude）協助提出選項與實作程式；每個階段在本機實際跑通、確認後才進行下一步。
- **理由**：每個設計都要能說明原因，不留黑盒子。

### D3. 文件解析：只用 Docling
- **選項**：只用 Docling／Docling＋輕量解析器（pypdf 等）／只用輕量解析器
- **決定**：只用 Docling，支援它能讀的格式（PDF、DOCX、PPTX、XLSX、HTML、圖片、Markdown…）。
- **理由**：條款、規章、手冊類文件的資訊常在表格與多層標題裡；Docling 會做版面分析，能還原版面、表格、標題階層，一般文字擷取工具做不到。
- **影響**：Docker image 會很大（含 PyTorch），第一次 build 較久；模型在 build 時先下載好，之後可離線。單元測試用假的 parser，不用載入模型。

### D4. OCR：只對圖片區域做 OCR
- **作者的想法**：Docling 會先做版面分析，分辨出哪些區塊是文字、表格、圖片；只要對**圖片**的部分做 OCR 就好。
- **決定**：照這個想法。Docling 的流程是 ① 版面分析（每頁都做，分類出文字／表格／圖片…）② 有內嵌文字的區塊直接讀取 ③ OCR 只針對「點陣圖片」覆蓋的區域（例如掃描頁、截圖、照片裡的字）。不開「整頁強制 OCR」。
- **影響**：文字型 PDF 幾乎不受 OCR 影響、速度快；掃描檔和圖片裡的字也讀得到。
- **待定**：繁體中文 OCR 引擎（RapidOCR／EasyOCR／Tesseract）實作時實測再選；圖片裡的字（例如圖表標籤）是否要放進搜尋，到解析階段用實際文件看效果再決定。

### D5. 切塊：結構優先，沒結構才用 sliding window
- **選項**：結構優先＋sliding window 備用／直接用 Docling 的 HybridChunker／只用 sliding window
- **決定**：有條文就依條文切、有標題就依章節切，都沒有才用 sliding window（有重疊）。切法做成可替換的「策略」，自己寫，不用套件內建。
- **理由**：條款、法規類文件以條文組織，依條文切塊能讓每一塊語意完整、引用精準到條號；沒有結構的長文則用有重疊的 sliding window，避免句子被切斷。單一條文超過長度上限時，在該條內用 sliding window 切，每塊仍標記條號。

### D6. 階層式檢索＋預先摘要
- **決定**：文件 → 區塊（一條條文／一個章節／一個 window）→ 小 chunk。搜尋用小 chunk；命中後找到所屬區塊，回傳**區塊摘要**。另有**全文摘要**（sliding window map-reduce：每框各自摘要後再合併，再長的文件都能處理）。
- **時機**：匯入時在背景產生，可以查詢進度。

### D7. 表格
- **決定**：表格轉成 Markdown，自成一個 chunk；大表依「列」切開，每塊重複表頭。帶頁碼，引用時能顯示「第 3 頁的表格」。
- **補充**：匯入時另請 LLM 讀表格的 Markdown，寫一段文字說明（例如「各通路的回饋比例與上限」），用於搜尋；顯示時仍呈現原表格。

### D8. 搜尋：向量＋關鍵字混合
- **決定**：向量搜尋（語意）＋ PostgreSQL 全文/關鍵字搜尋，再合併結果。
- **理由**：向量搜尋對「第 8 條」、專有名詞、數字這類精確字串很弱，而條款類問題很常包含這些（例如「第 8 條在講什麼」「保存幾年」）。評估集可以比較加和不加的差別。

### D9. Ollama 放在 Docker 容器
- **決定**：Ollama 當作 Docker Compose 裡的一個容器，`docker compose up` 一次全部啟動。
- **注意**：Windows 上要讓容器用 GPU，需要 Docker Desktop 的 WSL2 模式和夠新的 NVIDIA 驅動；不行就先用 CPU（較慢但功能正常）。

### D10. 前端：Vue 3
- **決定**：前端用 Vue 3，放在 repo 的 `frontend/` 子資料夾，用 Vite 打包。
- **影響**：電腦要另外安裝 Node.js。打包好的網頁要交給 FastAPI 還是另開一個容器提供，做到前端階段再決定。

### D11. 額外功能
- **納入**：簡單網頁介面、評估集（20～30 題「問題 → 應該命中的條文」，算命中率）。
- **未來改進（寫進 README）**：離線部署腳本（docker save/load）、GitHub Actions 自動測試。

### D12. 範例文件

- 來源不屬於本專案的文件：只在本機測試，不放進 repo。

### D14. 來源可展開原文
- **決定**：回答中的每個來源可點擊展開，顯示該段落的完整文字、頁碼與開頭文字（方便在原檔以 Ctrl+F 定位）。
- **理由**：摘要是濃縮過的，使用者需要能核對原文。系統不保存原始檔案，只保存解析後的文字，已足以做到。

### D15. 前端精準篩選
- **決定**：介面上方提供篩選：文件名稱、檔案類型（PDF、DOCX、PPTX…）；下方為語意問答。匯入時記錄原始檔名、檔案類型、上傳時間。

### D16. 支援格式與舊版 Office
- Docling 支援 PDF、DOCX、XLSX、PPTX、ODT/ODS/ODP、HTML、Markdown、CSV、EPUB、圖片（PNG、JPEG、TIFF…）等。
- 舊版二進位 Office（.doc、.xls、.ppt）：新版 Docling 透過 LibreOffice 支援，Docker image 需安裝 LibreOffice。實作時實測；若不穩定，改為先用 LibreOffice 轉成新格式再解析。

### D17. 專案主題：條款問答＋風險提醒
- **決定**：主題聚焦在**使用條款、隱私權政策**這類「大家都直接按同意」的文件。核心是條款問答（RAG）；招牌功能是**條款風險提醒**：上傳文件後，標出值得注意的條文並說明原因與條號。
- **理由**：條款文件以條文組織，正好發揮依條文切塊與精準引用的設計；風險提醒可直接建立在「逐區塊交給 LLM 處理」的既有機制上。範圍聚焦，才能用評估集把效果調好。
- **範例文件**：虛構的 App 使用條款、隱私權政策（含一份帶表格的文件，例如資料保存期限表）＋台灣公開法規（例如個人資料保護法，依著作權法第 9 條不受著作權保護）。真實服務的條款只在本機測試，不放進 repo。
- **沒選的**：信用卡推薦。它的核心是結構化擷取＋規則計算，和 RAG 不同，規劃為另一個獨立專案。

### D18. 切塊自動檢查
- **決定**：切塊不做逐塊人工校對，改用三層把關：① 程式自動檢查並標出異常（過短／過長的塊、應有條號卻沒抓到、欄數不一致的表格）② 換新文件類型時用切塊預覽頁抽查 ③ 以評估集的命中率判斷切法好壞。
- **理由**：逐塊校對無法隨文件量擴展；把人力集中在例外與規則設計上。
- **時程**：與階段 2（切塊預覽）一起實作。

### D19. 位置資訊（引用時顯示在哪裡）
- **決定**：每個 chunk 記錄 ① 條號／章節路徑（所有格式都有，主要定位方式）② 起訖頁碼（PDF、PPTX 才有；PPTX 為投影片編號）③ 開頭文字（方便在原檔以 Ctrl+F 定位）。XLSX 以工作表名稱定位。
- **理由**：DOCX、HTML 等格式沒有固定頁碼（分頁取決於開啟時的排版），只存頁碼會失準；條號不受排版影響。跨頁內容記錄起訖頁。頁碼採 PDF 閱讀器顯示的頁序，而非頁尾印刷頁碼。
- **待實測**：階段 2 以實際檔案確認 Docling 對各格式提供的位置資訊。
- **未來改進**：Docling 也提供段落座標，可做到「開啟 PDF 並標示該段落」。

### D20. 上傳後的處理：先同步，階段 5 改為 worker
- **選項**：D 同步等待／B API 內背景執行（BackgroundTasks）／A 獨立 worker 容器＋資料庫當工作清單／Celery + Redis
- **決定**：階段 2～4 先用**同步處理**（上傳後等處理完成才回應），程式最簡單、可專注在 RAG 本身。階段 5 加入摘要與風險判斷後處理時間變長，改為 **A：獨立 worker 容器**，API 只在資料庫寫入「待處理」，worker 領取工作執行並更新狀態（PostgreSQL `SKIP LOCKED`）。
- **理由**：同步處理在長時間工作時會逾時、看不到進度；B 會讓處理與問答互相拖慢，且重啟會遺失工作；Celery + Redis 對此規模過重。A 讓處理與問答分離、可顯示進度、重啟後可續做，且不需額外元件。
- **處理流程不變**：上傳 → 解析 → 切塊 → embedding → 可搜尋 →（背景）摘要與風險判斷。

### D21. 開發工具與專案結構（階段 1）
- **Python 3.12**：Docling 等主要套件皆支援的穩定版本。
- **套件管理：uv＋`pyproject.toml`**（選項：uv／`requirements.txt`＋pip）。uv 產生 `uv.lock` 鎖定所有套件的確切版本，Docker build 時以 `uv sync --frozen` 安裝，確保任何環境裝到的版本一致。uv 只在容器內使用，主機不需安裝。
- **資料夾**：後端放 `backend/`，與前端的 `frontend/`（D10）對稱；資料庫初始化 SQL 放 `db/init/`。
- **資料庫連線**：階段 1 僅以 psycopg 3 連線供 `/health` 使用；資料存取方式（直接寫 SQL 或使用 ORM）與資料表設計一併在 P3 決定。
- **安全預設**：資料庫不對主機開放 port，只有同一 compose 網路內的 api 能連線；帳密放 `.env`（不進版控），repo 只提供 `.env.example`。
- **`/health`**：檢查資料庫連線與 pgvector 版本；資料庫無法連線時回 HTTP 503。
